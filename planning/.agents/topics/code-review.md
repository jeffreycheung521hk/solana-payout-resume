# code-review：寫程式碼、審查與合併

- 載入：修改 `source/` 的程式碼、報合併、產出審查包時。
- 不載入：只改設計文件時。

## 寫程式碼時的分工

- 實作取捨按 `line.md`「線的須知」第 10 條判斷：滿足三個條件的先做後報，否則出卡。
- 子代理只寫測試或形狀已定死的機械程式碼；行為已由文件定死、程式碼量大的一塊，可以交給同級模型的子代理寫到編譯、clippy、測試都通過，再由線逐行複查最終 diff。要邊寫邊定的部分和小改動，線自己寫。
- 原因：業務邏輯最容易在細節上偏離已確認的設計，必須由負責的線逐行看過。

## 按批合併

- 一批之內，不管跨幾個 Session，程式碼都留在線的分支上；段末、Session 末都不報合併。
- 批末：線把分支 rebase 到 main、跑全套檢查，再報統籌；使用者表態之後由統籌併入。
- 設計寫回和術語表更新每批一次。
- 原因：按段報合併會把一批拆成好幾次合併，審查顆粒也太碎。

## 審查節點

- 開線時寫明在哪些節點審查、覆蓋哪些提交；沒寫的，統籌在批末問使用者這一批審不審。

## 審查包

- 審查線唯讀：檢出被審的提交，只寫 `records/review/` 底下自己的目錄。
- 首頁最多 10 項「要你看的」，按越晚改代價越大排序；每項附程式碼位置、對應的已確認設計和建議。
- 附件：偏離紀錄（包括線沒標出的偏離）、公開 API、組裝各部分的程式碼、外部輸入可達的風險位置、協定與設計條款的測試覆蓋、規則違反。
- 子代理報的問題，審查線對照程式碼核實後才放上首頁。

## 已確認設計本身的複核

- 審查包以已確認的設計為準，只能抓到實作偏離設計，抓不到設計本身的結構問題。若干批之後另做兩件事：
  - 縱向切片：提前打通一條最小的端到端路徑，用真實使用檢驗結構。
  - 設計覆盤：審查者不以設計理由為前提，只拿需求、協定和程式碼，針對被依賴最多的幾條結論，提出「這條確認錯了」的最有力論證。
- 原因：設計多半由使用者和 Agent 一起定，Agent 傾向認同既有方向；雙方一致不能證明方向對。
