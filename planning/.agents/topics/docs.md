# docs：讀者文件

- 載入：新增、修改、移動或刪除 `planning/docs/` 下的讀者文件時。
- 不載入：只改 `records/` 或程式碼時。

## 歸檔與格式

- 按決策主體歸檔：`planning/docs/payout-resume/` 屬於 solana-payout-resume；和別的專案共同的介面放 `planning/docs/shared/`。正文提到別的主體，不代表那個主體擁有其中的決策權。
- 每份讀者文件一個一級標題，標題後緊接恰好兩行中繼資料（`AGENTS.md` 不用）：

```text
> 文件歸屬：<主體，或跨主體的共同基線>
> 涉及主體：<正文實際規範的主體>
```

- 結論狀態只用三種：已確認（目前的設計共識）、建議待確認（有方向、未確認）、未決（實作者不得自行補全）。設計文件約定「未標註即已確認」。移動檔案、修連結、潤色都不改狀態。
- 正式名稱寫全稱。
- repo 內用相對連結；移動檔案時更新所有入站和出站連結，不留舊的佔位檔案。
- 新增、移動、刪除讀者文件時，先更新所屬目錄的 `README.md`，再視需要更新 `planning/docs/README.md`。
- 讀者文件不寫代理工作流、機器私有的路徑或只在本地成立的假設；代理工作流只寫在 `AGENTS.md` 與 `.agents/`。
- 整理、命名或修連結的任務，不順帶改變已確認的結論。

## 設計文件只留最新基線

- 方案從 A 改成 B 時，刪去 A，留下 B，以及「為什麼不是 A」「B 怎樣解決了 A 的問題」。
- 逐段判斷，取第一條成立的：
  1. 現行基線：保留，寫成現狀，按主題組織，不按討論日期。
  2. 現行結論的依據（協定條文、反例、失效路徑、測量）：放在結論旁邊。
  3. 被取代方案的教訓：刪掉後有人會合理地再提時，在「不採用的方案」留一條：它要解決的問題、具體缺陷、現行設計怎麼解決。
  4. 其餘刪除，只留在 Git 歷史：決定編號、稿次、日期、討論經過、推演的中間步驟、舊名的演變。
- 整理時不改結論狀態；刪一節之前，逐條核對其中的已確認結論、未決項和依據都已進入整理後的正文。整理與內容改動分開提交。
- 原因：按日期累積的紀錄讓讀者分不清哪些仍然有效，被取代的方案和舊名會在續接時被當成現行設計。

## 工程痕跡

- 交付物（程式碼、註解、讀者文件、提交訊息正文）不寫：任務歷史、工作日誌、驗證日記；Agent 或工具的名字；計畫裡的階段編號；讀者看不到的決定編號或文件；寫給統籌或使用者的話。
- 設計文件裡按約定標的結論狀態不算痕跡；日期、編號、稿次仍算。
- 本範例的兩個例外：根目錄 `README.md` 的主題就是這套工作流程，所以會寫到 Agent 與流程；提交訊息尾端的共同作者標記是工具的署名規定，保留在尾端，不寫進正文。
