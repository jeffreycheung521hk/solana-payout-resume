# terminology：術語與命名

- 載入：討論、寫文件、出提案或給程式碼取公開名稱時用到承載概念的名字；修改術語表時。
- 不載入：不涉及名字的機械修改。

## 術語表在哪裡、長什麼樣

- 總入口是 `planning/docs/glossary/README.md`。分表：`names.md`（品牌、專案、產品、外部程式，任何工作都讀）、`payout-resume.md`（付款中斷續接）。`conflicts.md` 記一名多義、一義多名、中英對不上的情況，每組附推薦叫法。
- 每個名字只在一張分表裡有條目。
- 每張分表分「本專案自造」「外部既有」兩節，各用一張七欄表：中文術語｜英文名／識別符｜概念｜來源｜狀態｜規範位置｜別名與舊叫法。英文名是條目的主名，判斷重名、是否改名都以它為準。
- 狀態以「已確認」或「建議待確認」開頭，括號裡寫所屬文件的狀態與日期；按命名規則定名的寫「已確認（按命名規則 n 定名，日期）」。
- 只收跨段落、跨文件承載概念的名字。欄位、區域變數、只出現一兩次的輔助名、標準函式庫型別不收；列舉變體寫進上位條目的別名欄；外部概念和本專案實作它的元件分成兩條。
- 程式碼的文件註解是介面行為的規範定義；術語表只登記離開那處程式碼也要用到的名字，寫一句用於辨認的話並指向程式碼。

## 用名字

- 先讀相關分表和名稱分表，再用名字；只讀相關的分表。
- 已有概念只用表中的叫法，不換同義詞；被取代的舊名不用於新內容；「建議待確認」的名字可以用，但所在方案要標為建議。
- 泛用詞寫出所指對象。例如「重送」只指送出同一份已簽位元組；「簽新的一筆」指用新的 blockhash 重新簽署。不用含糊的「重試」。
- 新名字的門檻：現有術語都不適用，而且概念會在多處反覆出現；否則用平實的話描述。原因：使用者審方案前要先記住每個名字，名字越多，審閱成本越高。
- 結構討論階段用平實描述或示意名；一輪結構確認之後按命名規則定名，不逐項請示。寫回時在回執與提交訊息列出每個新名：一句不依賴其他新名的含義、所依規則、不採用的名字。使用者可以事後改名。
- 只有這些情況出卡：規則覆蓋不到；兩條規則結果不同；要改一個已確認、規則也沒要求改的名字；名字是品牌、產品、代號或對外發佈的套件名。

## 命名規則

1. 同一類共用後綴，同組寫法一致；操作函式隨類型名改；列舉變體和模組名不帶後綴。
2. 範圍要準確：會和同類概念分不清時，名字寫出它屬於哪個對象；不會衝突就不加前綴。
3. 詞序是「機制、所屬對象、角色」，核心名詞放最後。
4. 名字說出它是什麼、有幾個，不讓人讀出它沒有的含義。
5. 事件列舉的變體按已經發生的事命名。
6. 外部既有的名字沿用原名，改成所在語言的大小寫慣例（`lastValidBlockHeight` → `last_valid_block_height`）。
7. 中英成分一一對應。
8. crate 名與協定識別符不用角色詞或品牌前綴；crate 名是「專案名加領域對象」，單一 crate 的專案直接用專案名。
9. 規則不追溯。Rust 名字另守通用慣例：錯誤類型以 Error 結尾而變體不帶；一種失敗一個變體；模組按它擁有的東西命名。
10. 中英對應在首次出現處綁定，寫成「中文（Identifier）」，之後兩種寫法都可以用。

## 改名與入表

- 不擅自改名：大小寫、前後綴、譯法的變動都算改名。發現一名多義、一義多名或中英對不上時，向使用者報告並記入 `conflicts.md`，附推薦叫法；不悄悄統一。
- 名字定下時才入表，和所屬文件的修改放在同一次提交；被取代的名字刪條目，舊名記在取代者的別名欄。
- 狀態取自所屬文件，不因為入表、反覆使用或已出現在程式碼裡而升級。
