# 決策包｜付款中斷續接的細節（5 項）

狀態：已呈現，等待裁決。呈現前的檢查見文末。

## 先對齊三個詞

- **一筆付款**：用 payout_id 識別，例如 INV-001；web3testproj1 把同一個識別碼叫 payment_id。一筆付款可以有多次**嘗試**，每次嘗試是一筆交易、有自己的簽章。「簽新的一筆」指同一筆付款底下的新嘗試。
- **落地**：交易被收進區塊，不論執行成功或失敗。
- **重送同一份**也涵蓋「繼續等」：還沒過期就重送同一份位元組，等下一次觀察。

| 前提 | 狀態 |

## 1. 範例範圍：只做離線模擬，還是加上 devnet 實跑？

**情境**　有人 clone 這個 repo，想親眼看到「送出 → 中斷 → 續接 → 沒有重複付款」。

**怎麼想**　這個範例要展示的是續接判斷和付款紀錄，不是怎麼組一筆 Solana 交易。判據有三個：讀者能不能在自己電腦一鍵重現；測試結果是否每次都一樣；你要審的程式碼有多少。

- **1a 只做離線模擬**（推薦）：寫一個模擬鏈，可以設定「交易在第幾個區塊落地」「哪一次嘗試會掉」「節點的帳冊從哪裡開始」。簽章和已簽位元組都是標明為合成的測試資料。前提：讀者接受範例不連真鏈。代價：證明的是判斷邏輯，不是真網路上的表現；範例裡的簽章不能拿去鏈上查。
- **1b 離線模擬，再加一個可選的 devnet 實跑**：在你自己的電腦用 devnet 測試幣真的送一筆，中途砍掉程序，再續接；第 5 項的匯出也能真的交給 web3testproj1 上鏈核對。前提：要加入 Solana 的簽署與 RPC 套件，以及一個有 devnet SOL 和測試 USDC 的錢包；這個工作環境連不到 devnet，只能由你在本機跑。代價：相依套件和審查量大幅增加；結果受 devnet 當下狀況影響，不能當固定測試。

**推薦 1a**，devnet 實跑可以留到下一批。

## 2. 付款紀錄存成什麼格式？要不要新增相依套件？

**情境**　程序寫紀錄寫到一半被砍掉，或寫完立刻斷電。接手者讀到的必須是完整的舊版或完整的新版；而且只要交易已經廣播，紀錄裡就一定要有它。

**怎麼想**　JSON 和逐行文字檔用同一套做法：先寫暫存檔並 fsync（要求作業系統把資料真的寫進磁碟，不只留在記憶體緩衝），再用 rename 蓋掉舊檔（同一個檔案系統內，rename 一次完成），最後 fsync 所在資料夾，讓「改名」本身也寫進磁碟。這幾步都做完才廣播交易；少了最後一步，斷電後資料夾可能退回舊檔，剛廣播的那次嘗試就不在紀錄裡。SQLite 則用自己的交易日誌達到同樣效果。所以格式的差別在可讀性、相依套件和要審的程式碼量。

- **2a 每筆付款一個 JSON 檔，新增 serde、serde_json、bs58 三個套件**（推薦）：三個都是 Rust 生態最常用的套件；JSON 你可以直接打開檢查。代價：多 3 個直接相依。
- **2b 零相依**：自己寫逐行文字格式和 base58 編解碼。前提：你願意多審約 150–200 行手寫解析。代價：手寫解析最容易藏 bug，而這裡正是不能出錯的地方。
- **2c SQLite（和 web3testproj1 一樣）**：前提：需要 C 編譯工具。代價：對「一筆付款一份紀錄」來說太重。

**推薦 2a**。

## 3. 「查遍歷史都沒有」怎樣才算數？

**情境**　Agent 停了三天才被接手（例如遇上連假），或接手時打到一台剛上線的新節點，帳冊只從幾小時前開始。舊交易早已過期，查詢回 null。一般 RPC 節點只保存大約最近兩天的帳冊，更舊的會清掉，查不到時同樣回 null。這種 null 只代表「它沒有那段資料」；這時簽新的一筆，就可能重複付款。

**怎麼想**　這跟查帳一樣：說「帳上沒有這筆」之前，要先確認帳冊涵蓋那段期間。會用到兩個 RPC 呼叫：

- `getSignatureStatuses` 查交易狀態，參數 `searchTransactionHistory` 設成 true 才會查歷史帳冊。下面的 `HistoryLookup` 是它的結果：找到、找不到、查詢失敗。
- `getFirstAvailableBlock` 回傳節點還保存的最早區塊，用 slot 表示。slot 是時間格子的編號，不是每一格都有區塊；判斷過期用的 block height 只數實際產出的區塊。兩者不能混比，所以這裡比的是兩個 slot。

交易不可能在取得 blockhash 之前落地，所以節點最早可用的 slot 只要不晚於「取得 blockhash 時的 slot」，那段期間就在帳冊範圍內。

```rust
pub struct Attempt {
    signature: Signature,
    signed_tx: Vec<u8>,
    last_valid_block_height: u64,
    blockhash_fetch_slot: u64,    // 新增：取得 blockhash 時的 slot
}

/// 兩個條件都成立，才算「查遍歷史都沒有」
fn history_proves_absent(attempt: &Attempt, obs: &ChainObservation) -> bool {
    obs.first_available_slot <= attempt.blockhash_fetch_slot
        && obs.history_lookup(&attempt.signature) == HistoryLookup::NotFound
}
```

- **3a 要求帳冊涵蓋證明**（推薦）：如上，條件不成立就交給人。代價：紀錄多一個欄位，每次判斷多一個查詢；而且它縮小風險、不是消除風險：最早可用的 slot 只證明起點，不能證明中間沒有缺口；兩個查詢如果經過負載平衡打到不同節點，結果可能對不上。
- **3b 直接相信帶 searchTransactionHistory 的 null**：前提：只用確定保存完整歷史的 RPC 供應商。代價：哪天換了供應商或節點設定，安全性會悄悄消失，程式自己察覺不到。
- **3c 過期之後一律交給人**：不自動判斷。代價：每一次過期都要人看，自動化只剩「重送同一份」。

**推薦 3a**，剩下的風險由第 4 項的上限兜底。

## 4. Agent 可以不經人核准就簽新的一筆嗎？

**情境 A**　INV-001 的第一次嘗試已過期，而且照第 3 項的標準確認沒落地。要不要自動簽第二次？
**情境 B**　交易落地了，但執行失敗（例如付款錢包餘額不足、收款方沒有 USDC 的 token account）。手續費已扣，錢沒轉出去。

**怎麼想**　B 只有一個合格做法：交給人。失敗多半出在輸入或帳戶狀態，自動重簽會以同樣原因再失敗、每次再付手續費，所以下面三個選項在 B 都是交給人，差別只在 A。A 的舊交易已確定不會再被處理，風險只在第 3 項的判斷本身會不會錯：判斷錯一次，就多付一次。

- **4a 自動簽，但一筆付款最多 3 次嘗試（含第一次），超過就交給人**（推薦）。前提：信任第 3 項，但用上限兜底：就算判斷每次都錯，最壞是同一筆付款被付 3 次，而不是無限次。代價：3 是任意選的數字，可以改。
- **4b 每一次新的嘗試都要人核准**：Agent 準備好，人按下去。代價：網路壅塞時，每一次過期都要等人。
- **4c 自動簽，不設上限**。前提：完全信任第 3 項。代價：判斷若有 bug，沒有任何關卡擋住。

**依賴**　第 3 項若選 3c，情境 A 不會發生，這一項自動等於 4b。

**推薦 4a**（上限 3 次嘗試）。

## 5. 匯出給 web3testproj1 對帳時，要匯出哪些簽章？

**情境**　INV-001 第一次嘗試過期、第二次成功。web3testproj1 讀一份 CSV（payment_id、交易簽章、付款人、收款人、mint、金額），逐列到鏈上核對；同一個 payment_id 第二次出現時，那一列改標「待查（needs_review）」，原因是 `payment_id_reuse`，但它自己的鏈上判定保留在 `reason_details` 的 `original_reason=` 裡。

**怎麼想**　判據是：對帳能不能獨立抓到續接邏輯自己的錯。假設續接判斷有 bug、兩次嘗試都落地而且轉帳成功，只有兩個簽章都交給對帳工具，才看得出來。這一項決定的是匯出規則：如果第 1 項選 1a，範例裡的簽章是合成的，web3testproj1 只能檢查 CSV 格式、無法真的上鏈核對；規則要到真實使用時才發揮作用。

- **5a 只匯出判定成功的那一次**：每筆付款一列，報告最乾淨。代價：對帳工具看不到其他嘗試，等於續接邏輯自己幫自己打分數。
- **5b 每次嘗試都匯出，判定成功的那次排第一**（推薦）：第一列照常核對，吻合就是 matched；其他嘗試被標成待查，看 `original_reason` 就知道是 `signature_not_found…`（沒落地，正常），還是 `finalized_direct_transfer_verified`（也落地而且轉帳成功，等於重複付款）。代價：只要重試過，報告裡就有待查列。

**推薦 5b**。
